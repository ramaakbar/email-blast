# 13 — Generate pipeline

**What to build:** Compose wizard steps 1, 2, and 5 working end to end: the user selects recipients (search/filter/select-all with a running count), picks a template whose required slots are covered by the selected recipients' metadata, and generates one PDF per recipient with live progress. Per-recipient failures are reported with reasons while the rest of the batch continues; the user spot-checks rendered PDFs before proceeding, and recipients whose generation failed are excluded from the send.

**Blocked by:** 11 — Recipients management, 12 — Templates

## Answer

Implemented in `email-blast-desktop/`:

- `src/shared/generate.ts` - NEW zero-dependency shared module: `resolveSlotValue` (name/email/phone win over the metadata bag, every other slot reads the bag by key), `slotCoverage` (per-slot missing counts across the selection - the wizard's fail-fast check), `sanitizeFileNameSegment` + `fillOutputName` (the output pattern becomes a file name, mirroring the legacy CLI's sanitizer). The renderer runs the same functions as the main process, so the coverage the wizard shows and the coverage the pipeline enforces can never drift
- `src/main/services/generate-jobs.ts` - the generate pipeline (the core of the ticket): `start` (creates a pending job + per-recipient rows), `run` (fill → convert → land, with the three-phase DOCX path: in-process docxtemplater fill per recipient into index-named intermediates, ONE LibreOffice headless invocation for the whole batch, then move each converted PDF to its final output-pattern name with `-2`/`-3` collision suffixes; the image path embeds the background per document and draws every declared slot centered in a default stacked layout), `getStatus`, `confirmedGoodAttachments` (the generate-then-send gate - only `generated` recipients with output on disk), `getRecipientPdf` (spot-check bytes). Progress events stream one per recipient in job order via the hub; job-level failures (template file missing, LibreOffice missing/crashing) fail the `run` effect and revert the job to pending; per-recipient failures (slot missing, fill/render error, conversion skipping a file, recipient deleted mid-job) mark that recipient failed with a reason and the batch continues. Errors are `Data.TaggedError`s: `GenerateJobNotFound`, `TemplateNotFound`, `LibreOfficeFailed`, `InvalidGenerateRequest`
- `src/main/services/progress-hub.ts` - the hub service: subscribe/emit, subscribed once at boot in `index.ts` and forwarded to every window via `webContents.send`
- `src/main/services/sqlite-repo.ts` - generate job statements: insert job/recipients, status transitions with `completed_at`, full job read with recipient names LEFT JOINed (deleted recipients show "(deleted recipient)"; the templates join is also LEFT so deleting a template never hides job history - it shows "(deleted template)"), per-recipient result writes, `getRecipientsByIds` in request order, `listAllRecipients` (unpaginated - the select-all source). The generate status unions now import from `shared/ipc` instead of re-declaring
- `src/shared/ipc.ts` + `ipc-channels.ts` + `preload/index.ts` + `src/main/index.ts` + `runtime.ts` - additive contract: `generate.startGenerate` / `runGenerate` / `getGenerateStatus` / `getRecipientPdf` + `recipients.listAll`, and the `generate-progress` event channel (preload `onGenerateProgress(cb)` returns an unsubscribe). All new handlers decode at the boundary and Schema-encode responses; `GenerateJobService.Live` + `ProgressHub.Live` joined the root layer; boot subscribes the hub to window forwarding
- `src/renderer/src/routes/compose.tsx` - the 6-step wizard: stepper shows all six steps with 3/4/6 locked (they belong to tickets 14/15). Step 1: search (250ms debounce), batch filter, checkbox table with cross-page selection, "Select all N matching" via `recipients.listAll`, running count, Next disabled at 0 selected. Step 2: template dropdown + preview card (type badge, slot chips, highlighted output pattern), coverage check with a per-slot missing report, Next blocked while uncovered. Step 5: campaign summary, Generate with live progress bar + generated/failed/pending counts, per-recipient failure list with reasons, spot-check with the first generated PDF rendered (pdf.js) alongside the recipient's data with prev/next browsing, Next enabled even with partial failures. The send handoff (`sendRecipientIds` = generated-only) is recorded for ticket 15 and shown on the step-6 placeholder; a staleness guard invalidates a finished job when the selection or template changes
- `src/renderer/src/components/pdf-preview.tsx` - NEW pdf.js canvas renderer (worker bundled as an asset, v6 `render({ canvas })` API); `template-badge.tsx` + `pattern-preview.tsx` extracted from `templates.tsx` so both screens render them identically
- `src/main/services/test-helpers.ts` - the fixture DOCX builder moved here from `templates.test.ts` (now shared by both test files)

Code review (two-axis: standards + spec, parallel agents) found 8 issues; the real ones were fixed and re-verified in the live app:

- The stepper made step 5 clickable before the coverage check passed, bypassing the Next gate; `reachable5` now requires `coverage.ok` (verified live: the chip is disabled while a slot is uncovered)
- A finished generate stayed "done" after the selection or template changed, leaving the spot-check and the send handoff bound to the old job; the done state now carries the bound selection/template snapshot and invalidates on mismatch (verified live: clearing the selection after a generate resets the handoff)
- Deleting a template hid its job history - `getGenerateJob` INNER JOINed templates; now a LEFT JOIN surfaces the job as "(deleted template)" (matches the no-FK-enforcement design from ticket 11)
- `generate:get-status` returned a raw value where every other handler Schema-encodes; now encoded like the rest
- The job-status unions were hand-declared in four places despite `shared/ipc` being the single source of truth; the repo layer now imports the shared types
- The `readonly current` on the image path's state type lied (the counter mutates it); removed. A `as { kind: "filled" }` cast on the batch-conversion input disappeared by tracking the filled files in a plain list during phase 1
- The deleted-recipient and missing-slot failure branches were duplicated across the DOCX and image paths; extracted into one `failRecipient` helper
- The invalidation effect initially read `generate.kind` without depending on it (oxlint exhaustive-deps); the bound-snapshot design above resolves it without a disable comment

Deviations from the spec, all deliberate:

- `cancelGenerate` (spec decision-4 table) is NOT implemented: the ticket checklist does not ask for it, the wizard has no cancel affordance for generate, and generation at ~0.22s/recipient finishes far too fast to need one; the schema's `cancelled` status stays reserved. Documented here so a later ticket can add it without re-deriving the shape
- Image-template text coordinates (CONTEXT.md places them at generate-job time) and @pdf-lib/fontkit (spec decision 2) are deferred together: no UI carries coordinates yet, and without a font source fontkit adds nothing. v1 draws every slot centered with the built-in Helvetica-Bold in a default stacked layout - Latin-1 names (the scholarship domain) render correctly; non-Latin values are the known limit
- The GenerateError taxonomy (spec section 9) is honored for job-level failures (typed tags over IPC); the per-recipient reasons (SlotMissing / DocxFillFailed / ImagePdfFailed / LibreOffice-skip semantics) are stored as the `error_message` TEXT column the schema provides - the UI displays them verbatim, and the DB column is TEXT, so there is no place for a structured tag
- `runGenerate` returns the finished `GenerateJob` where the decision-4 table says `void`: the renderer needs the authoritative snapshot and the run call is the natural place to get it (additive response, not a signature break)
- The spot-check starts at the first generated PDF and lets the user browse all of them, a superset of the ticket's "2-3" sample - the ticket's intent (check a few, not all) still holds
- The progress hub is a synchronous listener set, not the "bounded queue (256, drop-oldest)" of map decision 04: events are emitted and forwarded to `webContents.send` synchronously, so a queue would only buffer nothing; lossy tolerance already lives at the renderer boundary and SQLite stays the source of truth. Recorded here per the decision-04 intent
- `recipients.listAll` and `generate.getRecipientPdf` are additive channels beyond the decision-4 table - plumbing the ticket's own checklist ("select-all with a running count", "spot-check preview of 2-3 rendered PDFs"), following the ticket-12 `system:pick-template-file` precedent
- The wizard's step 1 is its own selection UI rather than reusing the Recipients screen: compose needs selection-as-state with select-all and no detail panel, a different interaction model from browsing; sharing one component would couple two screens that behave differently
- TestClock plays no part in the generate Seam A suite: the generate pipeline has no clock-dependent steps (pacing and retry live in the send pipeline, ticket 15, where TestClock does the work)
- `openDatabase` now opens with `enableForeignKeyConstraints: false` explicitly: the `node:sqlite` driver enforces FKs by default (verified with a probe), which would break the ticket-11 documented design of historical job rows surviving recipient deletes
