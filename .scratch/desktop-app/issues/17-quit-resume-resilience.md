# 17 — Quit/resume resilience

**What to build:** The app survives being closed mid-send. Window close or app quit during a running or paused job shows a uniform dialog on both platforms ("Send in progress - N of M sent. The job will pause and you can resume it later from Logs.") with [Quit & Pause] / [Keep Sending]; quitting pauses, never cancels. On launch, any job stuck in `running` (hard crash, power loss) is treated as `paused` - the persisted cursor is authoritative. Exactly one paused job produces a one-time launch banner; resume re-runs the SMTP pre-flight. Starting a new send while one is active is blocked with a message.

**Blocked by:** 16 — Logs & job detail, 25 - Effect codebase refactor

**Status:** resolved

- [x] Quit/close during running or paused job → uniform dialog with both branches; [Quit & Pause] quits with the job paused (never cancelled), [Keep Sending] cancels the quit
- [x] On launch: `running` jobs are treated as `paused` (cursor authoritative); exactly one paused job → one-time banner; resume from the banner or Logs re-runs the SMTP pre-flight before continuing from the first `pending` recipient
- [x] Starting a new send while one is running or paused-unresumed is blocked with a clear message
- [x] Seam A: relaunch-on-same-database resume continues from the cursor without double-sending; the one-active-job rule rejects a second job; the quit path loses at most one in-flight recipient

## Answer

Implemented in `email-blast-desktop/`:

- `src/main/db/repository.ts` - NEW `recoverInterruptedSends`: `UPDATE send_jobs SET status='paused' WHERE status='sending'`, returns the recovered count. The row data and persisted cursor are untouched.
- `src/main/services/send-jobs.ts` - NEW on the service shape: `recoverInterrupted` (the boot recovery), `activeJobSummary` (the quit guard's subject: a `sending` job, else the most recent `paused` one), and `launchBannerJob` (the one-time banner subject: exactly one `paused` job exists, else none). All three read through the existing `listSendJobs` summary rows, so the counts (`sentCount`/`total`) the dialog and banner need are the same shape the Logs table already uses.
- `src/main/index.ts` - the boot sequence now runs the recovery BEFORE any window exists (the first paint already sees `paused`, so the banner query at renderer mount is authoritative), and hands the `SendEnv` quit latch to the window. NEW window `close` guard: the active-job check runs SYNCHRONOUSLY (`Effect.runSync` over the same context - the repo queries are plain better-sqlite3), because a close that is not prevented in the same tick must proceed untouched - preventing it unconditionally would abort the `app.quit()` a window close normally triggers and strand the app alive with no window. When an active job exists, a uniform native dialog shows (`sendJob.quitInProgress`, parametrized N of M) with [Quit & Pause] / [Keep Sending] (`defaultId`/`cancelId` = Keep Sending, the safe default). [Quit & Pause] opens the quit latch (the run loop stops at its next checkpoint; the job stays `sending` with the cursor persisted) and quits; [Keep Sending] cancels the close. Quitting never cancels. `sendJob.quitInProgress`/`quitAndPause`/`keepSending`/`launchBanner` messages added to `messages/en.json` + `messages/id.json` (paraglide regenerated).
- `src/renderer/src/routes/__root.tsx` - NEW one-time launch banner in the app shell: `send.getLaunchBanner` at mount, refreshed by send-progress/job-paused events while visible (dismiss sticks for the session via a ref), Resume button running the same resume+run pair as the Logs button (run re-runs the SMTP pre-flight and continues from the first `pending` recipient after the cursor), error surfaced in the banner, `["logs"]` invalidated on completion.
- `src/shared/ipc-channels.ts` + `src/shared/ipc.ts` + `src/preload/index.ts` - NEW `send:get-launch-banner` channel / `Api.send.getLaunchBanner()`. No other new IPC: the quit guard calls the service directly against the boot context.
- Blocking a new send while one is running or paused-unresumed was already enforced in the service (`anySendJobActiveExcept` + `sendJob.anotherSendActive` from ticket 15); ticket 17 verifies it end-to-end (below) and reuses it unchanged. The dialog/quit seam ("quitting pauses, never cancels", at-most-one in-flight recipient) was already built into the run loop (`quitLatch` checks at the pacing gate, cursor persisted in the same transaction as the outcome) - ticket 17 wires it to the window lifecycle and adds the boot recovery that gives the `sending`-leftover its meaning.

Verification:

- Unit (Seam A, `send-jobs.test.ts`, NEW describe "boot recovery and quit guard"): recovery turns a stuck `sending` job `paused` with the cursor intact, a resumed run over a FRESH service delivers exactly the remaining recipients (no double-send), recovery is a no-op with nothing stuck; the banner is the single paused job and nothing for 0 or 2 paused jobs; the quit guard's active summary prefers `sending` over `paused`, and reports the counts the dialog needs. The existing quit-latch test still proves the loop stops between recipients losing at most the in-flight one.
- E2E (NEW `scripts/quit-resume-e2e.mjs`, packaged app, same pattern as `logs-e2e`): seeds a job stuck `sending` (cursor 2, one pending) + a never-run `pending` job; asserts the boot recovery (Logs shows "Paused - 2 of 3 sent"), the one-time banner naming the job, the one-active rule rejecting `runSend` of the second job with "Another send is in progress or paused" (driven through `window.api` in the live app), banner Resume delivering exactly one email against a local SMTP capture server and completing the job, and a new send running again once nothing is active. Zero renderer console errors.
- Regression: `logs-e2e` (the seeded paused job now raises the banner; it is dismissed up front so the original Resume selectors stay unambiguous), `i18n-e2e`, and `smoke-packaged` all still pass against the packaged app.
- Not E2E-coverable: the native quit dialog itself (Playwright cannot drive a native message box); its decision logic (active summary + latch open + quit) is the unit-tested seam, and the quit path's at-most-one-loss is the existing latch test. Typecheck, oxlint, and the full vitest suite (175) are green.

Code review (4 parallel agents over the diff) found three real issues, all fixed before commit: (1) a resumed job failing the SMTP/credential pre-flight reverted to `pending` with a persisted cursor - a state the UI has no resume path for; `run` now reverts such a job to `paused` (fresh cursor-0 wizard jobs still stay `pending` for their Try again), with two new unit tests covering both sides of that rule; (2) the banner's resume-success handler dismissed the banner even when the run ended `paused` via retry exhaustion - it now stays up for the paused job and only retires on a terminal run; (3) a second close/quit signal while the native dialog is open bypassed the guard - it is now prevented and the dialog's decision stands. A fourth finding (refresh the banner on every per-recipient progress event) was also fixed: progress refreshes only while the banner is visible, pause events always. All E2Es re-verified after the fixes.
