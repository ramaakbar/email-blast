## Answer

Implemented in `email-blast-desktop/`:

- `src/shared/send.ts` - NEW zero-dependency shared module: `extractMessageSlots` (the `{slot}` inventory), `messageValues` (the resolvable values of one recipient), `availableSlots` (the union across a selection - the autocomplete source), `messageCoverage` (unknown slots absent from every recipient vs slots missing for some), and `interpolateMessage` with an `escape` flag - the HTML body escapes every value, the subject interpolates plain. A missing slot throws a descriptive error, never a silent literal. The renderer runs the same functions as the main process, so the preview the wizard shows and the interpolation the pipeline enforces can never drift apart
- `src/main/services/send-jobs.ts` - NEW the send pipeline (the core of the ticket): `start` (validates the payload - exactly one SMTP identity, non-empty message/sender, existing recipients; the inline override's credential is stored with the job row and never crosses the bridge again), `run` (pre-flight = SMTP connect+auth plus at least one confirmed generated attachment on disk, failing fast and leaving the job pending/paused; then the send loop), `pause`/`resume`/`cancel`/`getStatus`/`retryFailed`. The loop per recipient: checkpoint (cancel / pause / quit-latch) → pacing gate (`Effect.race(sleep, wake)` where the delay is read live from the `rate_limit_delay_ms` setting each iteration) → build the message (interpolation failure fails that recipient without retries, batch continues) → 4 send attempts at t0/t0+1s/t0+3s/t0+7s (the spec's `Schedule.exponential("1 second", 2) x 3` timing, explicit for TestClock determinism) → outcome + cursor in ONE transaction (the critical section: send → persist → emit) → send-progress event. Retry exhaustion auto-pauses the job (persisted) and emits `job-paused` (reason `retry-exhausted`). Manual pause persists `paused` and wakes the loop through an in-memory control latch (unlimited pause/resume cycles, each run makes a fresh control). Cancel marks the remaining pending recipients `skipped` and the job `cancelled` in one transaction, then wakes the loop; the in-flight recipient's send completes and its outcome persists. The quit Latch (a `Latch` in the env) is checked at each checkpoint - tripped, the loop stops between recipients leaving the job `sending` (ticket 17's boot treats that as paused). One active send: `run` rejects while any job is `sending`. `retryFailed` rewinds the failed recipients to pending (error cleared), resets the cursor to the first of them, and returns the job to pending so `run` re-delivers exactly those
- `src/main/services/sqlite-repo.ts` - send job statements: `insertSendJob`/`insertSendJobRecipients`, `setSendJobStatus`, `persistSendOutcome` (the recipient row + the cursor in one BEGIN/COMMIT - a crash between them can never double-send or skip), `getSendJob` (full join with recipient names and the profile name, "(deleted recipient)"/"(deleted profile)" fallbacks), `cancelSendJob` and `retryFailedSendJob` (each one transaction; the retry cursor rewind counts rows before the first pending one - rowids span the table, so index arithmetic never uses them), `anySendJobSending`
- `src/main/services/smtp.ts` - `AttachmentNotFound` joins the SendError union (nodemailer wraps a missing attachment as ESTREAM but keeps the ENOENT wording - classified on both); `send(credentials, message)` delivers one message through a fresh transporter (no pooling - the runner owns pacing) and returns the message id; `getCredentials(profileId)` is the pipeline's only path to a stored credential
- `src/main/services/progress-hub.ts` - the hub now carries the discriminated `HubEvent` union (`generate-progress` / `send-progress` / `job-paused`, each tagged with `kind`); `main/index.ts` routes each kind to its channel (`send-progress`, `job-paused` added to the contract) instead of forwarding everything on `generate-progress`
- `src/shared/ipc.ts` + `ipc-channels.ts` + `preload/index.ts` + `main/ipc.ts` + `runtime.ts` - additive contract: `send.startSend` / `runSend` / `pauseSend` / `resumeSend` / `cancelSend` / `getSendStatus` / `retryFailedSend` + the two event channels (preload `onSendProgress`/`onJobPaused` return unsubscribes). All new handlers decode at the boundary and Schema-encode responses; `SendJobService.Live` joined the root layer (its layer provides GenerateJob, Smtp, ProgressHub, Settings, SqliteRepo - the duplicate entries merge away). `shared/settings.ts` gained `parseRateLimitMs` (clamp 500-5000, default 1000) shared by the gate and the wizard's slider
- `src/renderer/src/routes/compose.tsx` - all six steps live now (the lock is gone). Step 3: subject + HTML body textarea with a `{slot}` autocomplete dropdown (opens on `{`, keyboard navigable, inserts at the cursor), a live preview rendering the interpolated subject + HTML body in a sandboxed iframe for the first 3 selected recipients (a missing slot shows the descriptive error per sample), and a coverage report - unknown slots (absent from every recipient) block Next, missing-for-some warn while the batch would continue. Step 4: saved-profile or inline mode toggle, inline "Save as profile" (saves via `smtp.create` and switches to the saved profile), Test Connection with a live result strip (typed connect/auth errors inline), sender name+address, and the rate slider (500-5000, writes the same setting the gate reads live). Step 6: send summary, Start sends, live progress bar with sent/failed/pending counts, a scrolling per-recipient log with message ids and errors, Pause/Resume/Cancel (cancel confirms "N of M sent - cancel anyway?" via the native dialog), the paused state, the completion summary "N sent, M failed" with Retry Failures (re-runs exactly the failed recipients), and the cancelled state. The run flow re-subscribes to events on mount, so returning from another step mid-run picks the stream back up

Code review (five-axis, parallel agents over the working-tree diff - CLAUDE.md compliance, bug scan, spec/history, prior-ticket patterns, code-comment contracts) found 17 issues; the real ones were fixed, covered by new Seam A tests, and re-verified in the live app:

- Cancel (or the quit latch) landing while a recipient was mid-retry was overridden by the retry-exhaustion branch, which unconditionally paused the job AFTER the cancel transaction - the job could end `paused` instead of `cancelled`. The exhaust branch now re-checks `cancelRequested` and the latch and returns without persisting; a manual pause during the retries wins the `job-paused` reason. Same for the final recipient: the loop's `completed` stamp now re-checks cancel/pause/latch, so a terminal or paused decision is never overwritten by the finish line
- Pause-then-resume could run TWO send loops on the same cursor: pause returns as soon as the DB is paused while the old loop may still be delivering (socket timeouts to 30s), and a quick resume started a second loop that double-delivered the in-flight recipient. `run` now rejects while the in-memory control of the same job is still live ("This job is still pausing - try again in a moment"), and the wizard's Resume button stays disabled (`windingDown`) until the run promise resolves
- The one-active-job rule only blocked `sending` jobs, not paused-but-unresumed ones (spec section 5) - `anySendJobActiveExcept` now counts `sending` + `paused` excluding the job itself, so a paused job can always be resumed but blocks a new send
- The one-active check was not atomic: the job flipped to `sending` only AFTER the async pre-flight (connect timeouts to 10s), so two concurrent `run` calls both passed. The flip now happens BEFORE the pre-flight (the DB status is the guard), a pre-flight failure reverts the job to its prior status, and pausing during the pre-flight is legal
- The send event subscriptions leaked when leaving step 6 mid-run (each return added a permanent listener pair) - a cleanup effect unsubscribes on unmount
- Deterministic send failures were retried: a missing attachment file (AttachmentNotFound) or rejected credentials (SmtpAuthFailed) stalled the batch through the 1s/2s/4s backoff. They now fail the recipient immediately - retries are reserved for genuinely transient errors, matching the documented claim
- The wizard's send state had no staleness guard: after a completed send, changing the selection invalidated the generate handoff but left step 6 showing the OLD job's summary with no way to send the new one. The send state now resets with the handoff (the ticket-13 bound-snapshot pattern extended to its send counterpart)
- A stale "Connected" success strip survived editing the connection fields after a successful Test Connection - any connection change resets the test result
- A failed `startSend` (jobId null) dead-ended with no retry affordance - the error state now offers "Try again", and the Send button is disabled (with a hint) when no recipients have generated attachments
- The pacing clamp re-derived the slider bounds as literals instead of the shared `RATE_LIMIT_MIN_MS`/`RATE_LIMIT_MAX_MS`; the `SendStartPayload.delayMs` comment claimed the gate "snapshots" the value (it reads the live setting) and two "(future ticket)" references outlived their ticket - all corrected
- A blank recipient name silently interpolated to an empty string; `messageValues` now drops blank names so the missing-slot error fires instead
- The per-recipient log was duplicated across the live and snapshot renderers and had already diverged (the live list lacked names and skipped rows) - one shared row renderer with names seeded from the job at send start
- The step-4 mount effect reintroduced an `eslint-disable-next-line` (the ticket-13 review had redesigned that pattern away) - the rate-limit load moved to the wizard with a functional update, no disable comment
- New Seam A tests for every service-side fix: cancel during the retry backoff stays cancelled with no job-paused event; cancel during the last recipient's delivery is never overwritten by `completed`; a paused-unresumed job blocks a new send; a run while the same job is still winding down is rejected; an AttachmentNotFound send fails on the first attempt (exactly one send call)

Deviations from the spec, all deliberate:

- The step-4 "rate-limit override" slider writes the SAME `rate_limit_delay_ms` setting the gate reads live (spec section 5: "interval read live from the settings Layer each iteration... applies to a running job without restart"), and the job's `delay_ms` records the value at start for history. There is no per-job private rate: the wizard slider and the Settings slider are one control, so a live change applies to the running job and the job row keeps what was set
- `retryFailed(jobId)` retries ALL failed recipients where the decision-4 table says `retryFailed(jobId, recipientIds)`: the completion summary's Retry Failures is one click for the whole failed set, and the per-recipient retry belongs to the Logs screen (ticket 16), which can extend the call additively
- The `run` effect resolves with the finished `SendJob` where the table says `void` (the ticket-13 `runGenerate` precedent): the wizard needs the authoritative snapshot and the run call is the natural place to get it
- Retries are an explicit 4-attempt loop (t0, t0+1s, t0+3s, t0+7s) instead of `Schedule.exponential("1 second", 2).pipe(Schedule.times(3))` - the same timing, but deterministic under TestClock and free of Schedule edge cases; the Seam A suite measures the exact schedule
- `resume(jobId)` sets the status `pending` and returns the job; the caller then runs it (the wizard's Resume does resume + run). This keeps resume a fast state transition and leaves pre-flight ownership with `run`, which accepts both `pending` and `paused` jobs and re-runs the SMTP pre-flight either way (spec: "Resume re-runs the SMTP pre-flight")
- The per-recipient failure reasons (missing slot data, no confirmed attachment, retries exhausted) are stored in the `error_message` TEXT column as "Tag: detail" strings - the same serialization the IPC rejections carry, so the log shows what the user would see on the bridge
- One fresh SMTP connection per send (no pooling): the runner owns pacing per spec, and a per-recipient transporter keeps the retry attempts independent; the connection cost is negligible at the 500-5000ms gate
- The quit Latch exists and is checked at every checkpoint, but nothing opens it yet - opening it on quit is ticket 17's window-close dialog flow; the seam and its at-most-one-in-flight guarantee are proven by Seam A
